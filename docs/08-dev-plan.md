### 范围与开工顺序

1. **先 shared 契约，再数据库结构与升级。** 统一 Zod 枚举 / 类型 / actions / DTO：订单 `voided` 和取消申请状态、核销 `direct/prepaid`、退款、无金额发货视图、只读财务售后视图、完整财务核销历史、外部精简记录、需求日期 / 排序 / 来源、三种快照令牌及实时通知。增加 `order_cancel_requests`、`payment_allocations`、`refunds`、`wh_doc_images` 和所需版本 / 撤回字段、文件 `loss_image`、退款号 `TK`；取消实发不超过订单数约束，移除旧每单一笔有效付款限制及付款单据外键。历史 SQL / journal 不改，验证空库建库及旧结构升级。旧付款回填单独脚本，按下节先在本地验证。
2. **后端按业务块改，每块测完再继续。** 权限、归属、版本、actions 与数据库事务共用实现，不能只隐藏按钮。订单取消申请的申请 / 撤回 / 同意 / 拒绝 / 发货失效全部提升父订单版本；作废订单和售后、采购收货及作废等按 05 §10.1 统一主体账本锁与稳定行锁顺序。纯发货不能读销售金额 DTO，兼岗 / 管理员的专用发货投影也不含金额；财务售后入口即便兼岗也只读。
3. **完成财务核心，再接各业务读写。** 收付对称登记、预收 / 预付核销、单条撤回、退款及退款作废；资金和核销均按登记时间 / ID 重算，不按补录业务日期重排。单据改额可能使后续单据重新待结，金额为 0 但未撤回的有效核销仍拦业务作废。采用 `ledgerToken + expected` 全账复核、条件版本更新、幂等重放、完整历史与所有受影响对象的提交后通知。待付只列未付大于 0；对账保留有效且应付大于 0 的未付 / 部分付 / 已付单。有效与作废退款都有历史、仅有效算余额。旧 `pay` 动作和旧按单付款 / 复核契约随消费者切换删除，不保留两套业务流程。
4. **同步采购与目录能力。** 需求卡片用每种花材的实际 `shipFrom/shipTo`，不能用筛选 `from/to`。订单确认、销售新建 / 修改 / 取消 / 发货、产品及目录共用配方、库存 / 在途变化后自动通知并刷新需求，绝不自动下单、邀请或出库。默认全部、缺货优先、可切只看缺货；独立过期提醒；在途采购单来源及「在途不代表已到库」。已有邀请只提醒、可看原邀请；新建采购单 / 邀请用 `reviewToken` 复核最新缺口，保留输入、允许超缺口购买，再变化需再次核对。供应商只改 / 取消自己填报生成的待收单；仓库按归属作废已收单。空目录复制用 `previewToken`，空分类可复用，零可复制项不写，来源 / 目标变化需重预览，复制与普通目录维护共享锁。
5. **最后改小程序页面与交互。** S6 / X3 取消申请，H2 / H3 少发多发及无金额视图，售后必传图，X11 复制目录，C2 / C5 / C7 需求同步与核对，P2 / P6 供应商改单取消，W3 作废采购单，F3 / F4 / F6 / F7 / F8 登记和核销 / 退款 / 完整历史；P5 保留已付单与预付 / 退款状态。编辑中的实时变更不覆盖草稿，失效令牌需要明确重核；`version: null` 的派生变更也强制重读。M6 日志取自身历史模块，调岗不抹去自己的非公共历史。
6. **更新验收而不是兼容旧用例。** 按 07 新增 / 修改用例补对应层测试，修正旧状态、旧按单付款弹层、日志岗位过滤、有效核销隐藏零值、盘点作废等不符新规则的断言；接口与界面分层。每完成一块跑该块测试再继续，最终做相关全量回归并给 diff 汇总。不提交、不部署、不碰线上。

上述 UI 范围对应 `server/src`、`miniapp/miniprogram`、`shared/src`，不是仅新增四张表。重点还包括当前需求 SQL / DTO / 卡片、统一 actions 与错误投影、历史核销读模型、全账重算引发的跨单据实时同步，以及文件上传用途和归属校验。

**阶段 5 边界：** 手工入库接应付、出库 / 报损作废及图片、盘点和相应页面仍随阶段 5 实施。返工阶段可以先补所需契约 / 表结构 / 共用财务能力，不能因此声称这些页面已验收；07 仓库 C06–C13、C15–C18、C20–C26 及其他涉及手工单据的分支在阶段 5 通过。其余阶段 3、4 返工用例通过后再开阶段 5，完成标准同下文。

### 本项目已上线旧付款的升级方案

这是当前重写项目自身版本升级，包含已上线 `ruirui-010` 的旧付款；不是迁移排除范围里的古老花众系统。本轮只定方案，不连接线上或执行迁移。线上实际结构、版本、迁移 journal 与付款记录数量，必须以后获授权核实，不能仅凭本地 `b04a3ce` 推定。

**白话原则：** 以前一笔付款只能挂一张采购单；升级后保留这笔钱本身，再补一条「这笔钱用于原采购单」的核销记录。作废过的钱保留作废历史、核销也已撤回，不重新当成付款，不凭空造退款或预付。

1. **扩展。** 保存可恢复备份和付款→原采购单映射，先建新表、版本 / 撤回字段和可回填结构；旧 `po_id`、原约束与唯一索引暂留。准备枚举升级，旧实例与新实例不得混用两套财务写入语义。
2. **回填（独立脚本，先 dry-run）。** 每条旧付款对应一条 `direct` 的 `payment_allocations`，关联原采购单、金额取原付款；原付款 ID / 单号 / 日期 / 金额 / 方法 / 登记人 / 状态 / 作废信息不变。核销 `created_at/created_by` 取原登记时间和登记人，不能全写迁移时刻打乱顺序；`updated_at` 明确保留来源。旧有效付款生成未撤回核销；旧作废付款生成已撤回核销，`revoked_at/by/reason` 取原作废元数据。旧收款 `allocations.kind` 从 `receipt` 转 `direct`，`prepaid` 不变；历史整笔作废导致的撤回字段可从原收款作废元数据补全，缺失则阻断，不猜人或时间。
3. **异常阻断与幂等。** dry-run 检查付款→单据存在、双方供应商一致、有效付款目标状态 / 金额匹配、无多笔有效付款、金额合法、登记 / 作废元数据完整。异常生成清单、停止正式回填，不自动改单、转预付、造退款。用独立受控迁移映射或等价可靠标识唯一对应旧付款与回填核销；断点 / 重跑不新增重复核销，已回填来源变化要阻断。不能给正式 `payment_allocations.payment_id` 加唯一约束，一笔钱正常可核销多张单。
4. **核对。** 逐行核付款身份、金额、状态、操作人及时间不变；逐单、逐供应商核有效已付 / 待付相同，作废付款生效为 0；正常旧数据迁移后预付为 0，无自动新增退款。既有收款 / 核销的金额与顺序不改。不能只比较一个总额；有异常不得收缩或放开写入。
5. **收缩与切换。** 核对完成、新读模型验证后再移除付款 `po_id` 外键 / 非空列与每单有效付款唯一索引，允许一笔付款不核销或核销多单。迁移映射保存在受控备份 / 批次产物，不成为正式业务第二套账。处理旧 `idempotency_keys.response` 与新 DTO / 枚举不符的问题：保留请求去重身份及原业务结果，旧成功请求重试只能识别为已处理 / 返回对应新视图，不重新入账，不直接删键。

**迁移工具限制：** 当前 `server/db/migrate.ts` 使用的已安装 Drizzle PostgreSQL migrator 会把所有待执行文件放在一个事务。PostgreSQL `ALTER TYPE ... ADD VALUE` 新增的枚举值，在事务提交前不能立刻用于 CHECK / DEFAULT / 回填；分成两个 SQL 文件不等于两个事务。实施时验证真正已提交的分阶段升级，或采用适合本次类型的安全变换；不改已应用的 0000–0004 历史 SQL / journal。旧枚举重命名也会影响仍在运行的旧写入端，必须与停写切换配合。

**本地验证：** 使用 `b04a3ce` 原结构、种子及专门的旧付款夹具先造旧数据，再跑升级。当前种子没有付款，单跑新种子不能代表迁移验证。覆盖有效已付、作废未再付、作废后重付、停用供应商 / 方式、多供应商、同日不同登记顺序、异常阻断、重复执行、事务失败回滚、枚举转换和旧幂等键重试，按 07 §10.1 的 K01–K08 验收。脚本单独写，先在本地验证，不碰线上。`db:reset` 会迁移并灌种子，不是生产升级工具。

**以后另获授权才执行线上切换：** 核实真实版本 → 财务停写且隔离旧实例 / 旧客户端写接口 → 备份并验证可恢复 → 最终映射与回填 → 逐层核对 → 收缩 → 新版启用 → 冒烟。不能只关小程序页面而留后端旧写接口开放。新版本产生多单核销、部分付款、预付或退款后，旧模型无法无损表达，不能直接回滚旧代码；新写入前可按备份整体恢复，新写入后先停写评估前向修复 / 完整恢复，不能为回退抹掉实际发生的钱。
