# 00 工程原则与接口契约

整理日期：2026-09-30。其他各章都要遵守本章。和本章冲突的写法，一律按本章改。

## 1. 分工：后端定规则，前端管交互

| | 后端 | 前端 |
|---|---|---|
| 权限 | 每个接口按角色和数据归属做最终校验 | 只按后端返回的结果显示或隐藏入口，不自己判断角色 |
| 业务规则 | 状态流转、前提条件、数量上限、互斥，全部在后端做最终校验 | 不重复写业务规则 |
| 能做哪些操作 | 每张单据返回 `actions`：当前账号在这张单上能看到的操作按钮，一个列表，每项 `{ code, enabled, disabledReason, reasonRequired }`。`enabled: false` 表示按钮显示成禁用，`disabledReason` 写原因（例如门店停用时的「确认订单」：「门店已停用，启用后才能确认」）；`reasonRequired` 表示提交时必须写原因（例如取消待发货的订单）；不适用的字段为 `null`。能不能换供应商这类，也用操作码表达（例如 `changeSupplier` 在不在列表里），不另加 `xxxLocked`、`xxxEditable` 字段。需要写状态提示时另返回 `lockedReason`（一句话，可以和 `actions` 同时出现，没有就是 `null`） | 按 `actions` 显示按钮：`enabled` 为 true 的可点，false 的显示禁用并写 `disabledReason`；按 `reasonRequired` 决定弹层里要不要原因框；按 `lockedReason` 显示状态提示。不根据状态自己推算。只和本页输入有关的条件（例如还没勾选花材）由前端自己禁用 |
| 金额、库存 | 应收、应付、预收、已收、未收、可申请数量、余量都由后端算好返回 | 只显示，不计算。例外：表单里边输入边显示的行金额、合计、盘点差异，以及从余量带出的缺口（`gapOf(leftQty)`），用 `shared` 里前后端同一个函数算，提交后以后端返回为准 |
| 校验 | 用 `shared` 的同一份 Zod 规则做最终校验 | 用同一份规则即时提示，减少来回；提交结果以后端为准 |
| 界面 | — | 交互、展示、加载、空、断网、报错、提交中、实时提示（02 章第 5 节） |

这样同一条规则只写在一个地方。前端只负责把后端的判断显示出来，不会和后端各算一套、算出不同结果。

## 2. 接口契约：一份定义，前后端共用

- 所有接口定义在 `shared/contract`，每个接口只定义一次：方法、路径、允许的角色、请求结构（Zod）、响应结构（Zod）、可能返回的错误码。
- 后端的 controller 绑定契约：入参按请求结构校验，出参在测试环境按响应结构校验。契约里有、后端没实现的接口，测试直接失败。
- 前端的请求方法从契约生成，参数和返回值都有类型。页面不手写路径，也不手写接口的类型。
- 改接口只改契约。改完之后，前后端哪里没跟着改，类型检查就会报错。

## 3. 统一的字段、类型、格式

| 内容 | 契约里的格式 | 说明 |
|---|---|---|
| 字段名 | camelCase | 数据库 snake_case，只在数据层转换一次 |
| ID | 字符串 | 数据库是 BIGINT，接口统一传字符串，避免超出 JS 数字精度 |
| 单号 | 字符串，`前缀-YYMMDD-三位序号` | 后端发号，前端原样显示 |
| 金额 | 整数「分」，字段名以 `Cents` 结尾 | 例如 `amountCents: 13600`；只在显示时格式化成 ¥136.00 |
| 数量 | 整数 | 单位另给 `unit` 字段 |
| 业务日期 | `YYYY-MM-DD` 字符串 | 出货日期、入库日期；按 Asia/Shanghai 算 |
| 时间戳 | ISO 8601 UTC，例如 `2026-09-30T00:10:00.000Z` | 前端格式化成上海时间显示 |
| 状态 | 英文枚举码，例如 `to_ship`（待发货） | 中文名和颜色只在 `shared` 的状态表里定义 |
| 空值 | 可选字段一律返回 `null`，不省略 | 前端不用区分「没有」和「没返回」 |
| 列表 | `{ items, nextCursor }` | 分页统一用游标 |
| 版本号 | `version` 整数 | 写操作必须带上 |

## 4. 统一的响应和状态码

- 成功：HTTP 200，`{ ok: true, data }`。
- 失败：`{ ok: false, error: { code, message, fields, latest } }`，HTTP 状态码和错误码固定对应：

| 错误码 | HTTP | 含义 |
|---|---|---|
| `UNAUTHENTICATED` | 401 | 没有绑定账号 |
| `ACCOUNT_DISABLED` | 403 | 账号已停用 |
| `FORBIDDEN` | 403 | 没有权限 |
| `NOT_FOUND` | 404 | 找不到 |
| `VALIDATION_FAILED` | 422 | 字段不对，`fields` 写每个字段的原因 |
| `STALE` | 409 | 状态或版本变了，`latest` 带最新数据 |
| `BUSINESS_RULE` | 409 | 业务规则拦住，`message` 是给用户看的一句话 |
| `INTERNAL` | 500 | 系统出错，带请求编号 |

- 错误码、HTTP 状态码、默认文案都定义在 `shared/errors`，前后端引用同一份。
- 前端只按 `code` 处理（02 章第 5.3 节），不解析 `message` 的内容。
- 越权访问：读写别家门店、别家供应商的数据，返回 `NOT_FOUND`，不暴露这张单据存不存在；角色本身没有这个模块的权限，返回 `FORBIDDEN`。唯一例外是供应商填报邀请的分享链接：别家供应商的账号打开时返回 `FORBIDDEN`，页面显示「这张邀请不是发给你的」。

## 5. 不硬编码

- 状态、角色、操作、单据类型、错误码：`shared` 里的枚举。
- 界面文案：`shared/copy`。后端返回给用户看的句子也从这里取。
- 业务参数：`shared/config`，例如售后图片张数和大小、采购需求默认天数、单号格式、分页条数。配置名和初始值只列在 05 章第 1.6 节，其他章只引用配置名。
- 设计值：`styles/tokens.wxss`。
- 环境相关（环境 ID、服务名、COS 桶、数据库连接、密钥）：环境变量，不进代码。
- 示例数据只在 `db/seed` 里，业务代码不认识任何具体的门店、产品、账号。
- 检查：ESLint 禁止在业务代码里写状态中文、魔法数字、颜色值（`shared` 和 `tokens` 除外）。

## 6. 统一收敛：一件事只有一种写法

- 前端：请求只走 `core/request`，实时只走 `core/realtime`，格式化只走 `shared/format` 和 WXS 工具，放弃修改只走 `core/guard`，界面状态只用 `hz-state`、`hz-error`、`hz-notice`。
- 后端：权限只在守卫和数据归属过滤里做；事务、日志、幂等、版本号复查、实时通知由公共层统一处理，业务代码不重复写。
- 同样的查询（例如应收计算、库存可用量）只写一个函数，各模块调用它，不复制。
- 发现两处写法不一样，合并成一处，不再新增第三种。

## 7. 不打补丁、不留死代码和冗余代码

- 修 bug 先写一条能复现的测试，再改根因。不在调用处加特殊判断绕过去，不加「兼容旧写法」的分支（没有历史数据要兼容）。
- 规格变了就改规格书和契约，再改代码，三者保持一致。
- 不留注释掉的代码、没用到的导出、没人调用的接口、没人进入的页面、「以后可能用」的参数。CI 用 knip 检查未使用的文件和导出，有就失败。
- 不写 TODO 就合并。没做完的事记在规格书或任务里，不写在代码里。
- 不写冗余代码：
  - 同一段逻辑只写一次。第二处要用就抽成函数或组件，不复制粘贴。CI 用 jscpd 检查重复代码，超过阈值就失败。
  - 能从契约、表结构生成的（类型、校验、请求方法）一律生成，不再手写一份。
  - 不加没有实际作用的封装层：只是原样转发参数的函数、只有一个实现的接口、只被用一次的「通用」工具，都不写。
  - 接口不返回能从别的字段推出来的冗余字段。能不能操作只看 `actions` 和 `lockedReason`（第 1 节），不再另加 `xxxEditable`、`xxxLocked`、`xxxRequired` 这类布尔字段表达同一件事。
  - 同一个意思只有一个字段名，不出现同义字段。
  - 不为「以后可能用」预留参数、配置、表字段和页面。

## 8. 不容易出 bug

- TypeScript 严格模式，禁止 `any`，契约类型贯穿前后端。
- 数据库用约束兜底：`CHECK`（金额、数量不为负）、外键、唯一约束、部分唯一索引。代码写错了，数据库也不会存进错数据。
- 并发只用两种手段：版本号条件更新、行锁（`FOR UPDATE`）。互斥清单见 03 章第 6 节，每一对都有测试。
- 金额只用整数分计算，不用浮点数。
- 07 章的验收用例就是回归测试，每次提交都跑。

## 9. 性能

目标（4G 网络、中端机，由我默认，可以改）：

| 指标 | 目标 |
|---|---|
| 冷启动到首屏可看 | 2 秒内 |
| 页面切换到内容出现 | 1 秒内（骨架屏立即出现） |
| 常用接口响应（后端处理） | 200ms 内 |
| 列表滚动 | 不掉帧 |
| 主包体积 | 1.5MB 以内 |

做法：

- 前端：按角色分包并预下载；`setData` 只传变化的字段，不传整页数据；列表分页（每页 `PAGE_SIZE` 条）；图片只加载缩略图并懒加载；字体子集化；组件按需引入。
- 后端：每个列表和筛选条件都有对应索引；汇总（对账、待办、采购需求）一条 SQL 算完，不在循环里查库；接口返回页面需要的字段，不返回整张表；数据库连接池。
- 实时推送只带「哪张单变了」，不带内容，推送量小。
- 性能测试：用种子数据放大到一年的量（例如 1 万张订单）跑一遍关键列表和对账，达不到目标不上线。

## 10. 全面不冗余：每件事只有一个出处

不光代码，下面这些也一样：同一件事只在一个地方定义，其他地方引用它，不复述。

| 方面 | 规则 |
|---|---|
| 规格书 | 每条规则只写在一章：工程原则、统一字段格式、错误码和 HTTP 状态在 00；技术选型在 01；视觉、界面状态和显示格式在 02；业务规则在 03；表结构在 04；每个接口的定义和操作码表在 05；页面在 06；用例在 07。其他章要用就写「见 03 章第 5 节」，不再抄一遍。改规则只改一处 |
| 数据 | 一个事实只存一份。能算出来的不存（应收、应付、预收、收款状态、`actions`）；同一个信息不存在两张表里（例如供应商端账号只在 `accounts`）；不存「冗余字段方便查询」，靠索引和查询解决 |
| 接口 | 一个意思只有一个字段名；不返回能从别的字段推出来的值；同一份数据不开两个接口（列表项和详情共用同一套字段定义，详情只多明细） |
| 界面 | 同一种区块只有一个组件（变更记录、改价记录、状态提示、对账格各一个）；同一个功能只做一个页面或弹层，可以从多个相关位置进入，但每个入口都要带上当前页面的数据进去（例如从订单详情申请售后，自动选好这张单）；不带数据、只是重复的入口不放；页面上不重复顶栏已经写过的信息；不放规则说明文字 |
| 文案 | 每句文案只在 `shared/copy` 里定义一次，前后端引用同一个键；同一个意思只有一种说法（例如「未收」和门店端「待付」这种有意区分的写进对照表，其余不出现近义词） |
| 配置 | 每个参数只在 `shared/config` 或环境变量里出现一次，不在文档、代码、测试里各写一个数字 |
| 设计值 | 颜色、尺寸只在 `tokens.wxss` 定义一次，TDesign 主题也引用它 |
| 测试 | 同一条规则只在一层测：权限和业务规则在接口测试，界面展示在前端自动化，不在两层重复断言同一件事；测试数据只有一份种子 |
| 流程 | 每类检查只做一次、只在一处跑（lint、类型、测试都在 CI），不在多个脚本里重复配置 |

发现两处在说同一件事：保留更合适的那一处，删掉另一处并改成引用，不新增第三处。

## 11. 代码质量标准

前面几节（契约、统一收敛、不冗余、不打补丁、防 bug）是底线，本节补上「写得好」的具体标准。标准能用工具检查的都放进 CI，检查不过不合并。

### 11.1 命名

- 代码里的业务名词只用 `shared/glossary` 里的英文名：一个中文词对应一个英文名（例如 待发货 = `to_ship`、应收 = `receivable`、核销 = `allocation`），不各起各的。
- 名字说清是什么、做什么：函数用动词开头（`confirmOrder`、`calcReceivable`），布尔用 `is`、`has`、`can` 开头，不用 `data`、`info`、`temp`、`handle2` 这类名字，不用拼音、不用缩写（通用的 `id`、`url` 除外）。

### 11.2 结构

- 后端分三层，依赖只能往下：
  - controller：只做契约校验和调用 service，不写业务逻辑。
  - service：业务流程、权限归属、事务。
  - repository：只做数据读写，不写业务判断。
- 业务计算（金额、可申请数量、余量、`actions` 判断）写成纯函数，放在 `shared/domain` 或各模块的 `domain` 目录：输入数据、返回结果，不查库、不读时间、不改参数。这部分最容易测，也最不容易出错。
- 模块之间只通过对方公开的 service 方法调用，不直接读别的模块的表，不 import 别的模块的内部文件。ESLint 规则限制跨模块 import。
- 小程序页面只做三件事：取数据、把数据交给组件显示、把用户操作交给请求层。页面里不写业务判断。

### 11.3 复杂度上限（ESLint 检查）

| 项 | 上限 |
|---|---|
| 单个函数 | 50 行，圈复杂度 10，嵌套 3 层，参数 4 个（多了用对象参数） |
| 单个文件 | 400 行 |
| 单个组件 | 一个组件只做一件事；属性超过 8 个说明该拆 |

### 11.4 错误处理

- 业务错误统一用 `shared/errors` 里的错误类型抛出，公共层转成第 4 节的响应。业务代码里不直接拼 HTTP 响应。
- 不吞错误：没有空的 `catch`，不用 `catch` 返回默认值掩盖问题。
- 只在边界做防御：接口入参、外部服务返回、数据库结果在边界校验一次；内部函数之间靠类型保证，不层层重复判空。

### 11.5 测试

- `shared/domain` 和各模块 `domain` 的纯函数：行覆盖率不低于 90%，每条规则的边界值都有用例（0、刚好等于上限、超过上限）。
- 后端 service 和接口：07 章接口测试用例全部通过；每对互斥操作都有并发测试（03 章第 6 节）。
- 测试名写业务结果，例如「售后金额超过发货金额时拦截」，不写「test1」。
- 测试之间不共享可变状态，每个测试自己准备数据，顺序打乱也能过。

### 11.6 每次改动的完成标准

一次改动（一个功能或一个修复）要同时满足：

1. 规格书、契约、代码三者一致：规则变了先改规格书，再改契约，最后改代码。
2. CI 全绿：类型检查、ESLint、Stylelint、knip、jscpd、单元测试、接口测试。
3. 新增或改到的规则有对应测试；修 bug 有复现测试。
4. 没有新增冗余、死代码、写死的值、TODO。
5. 我自己按 diff 通读一遍再交付，说明改了什么、测了什么、还有什么没做。

### 11.7 提交

- 一次提交只做一件事，提交说明用中文写清「做了什么、为什么」。
- 依赖用精确版本，新增依赖要说明用途；能用已有依赖或几行代码解决的，不加新依赖。
